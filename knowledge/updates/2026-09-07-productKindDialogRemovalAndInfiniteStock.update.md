# Product kind dialog removal + unlimited stock — 2026-09-07

Supersedes the "Add product" half of
[`2026-09-06-digitalProductsFinalMessage.update.md`](./2026-09-06-digitalProductsFinalMessage.update.md)
(the `ChooseProductKindDialog` it introduced is gone). The `kind` field, `ProductKindSection` and
the whole final-message feature described there are unchanged.

## Problem

Two things, both raised by the user.

1. **The physical/digital dialog was in the way.** «افزودن محصول» opened
   `ChooseProductKindDialog` before the editor mounted, and the answer only pre-set a control the
   editor already has (step ۱، `ProductKindSection`) and which stays editable afterwards anyway. It
   was a mandatory question for something the merchant could change one screen later.

2. **Steps ۶ and ۷ silently did nothing for a product with no attributes**, and the quantity field
   had no "unlimited" option at all.

   The second half is the load-bearing one. `BasePriceSection`/`BaseStockSection` wrote **only**
   `basePrice`/`baseCompare`/`baseStock`. Those are seeds: the sole reader is `useVariantSync`,
   which copies them into rows **it generates**, and generation only runs on an axis edit
   (`combosOf` returns `[]` with no axes). So for a product that never got a رنگ/سایز:

   - nothing was ever generated, so nothing ever read the seeds;
   - the product's real price and stock live on its one implicit variation
     (`buildEmptyProductForm`'s single blank row, rendered in the grid as «محصول بدون ویژگی»);
   - Save then failed zod's `priceRequired`/`stockRequired` on `variants.0.*` and jumped the
     merchant down to a grid row to retype what they had just typed at the top of the page.

   Meanwhile the grid row had an ∞ button and the card above it did not, so "unlimited" was
   reachable only from the table.

## Solution

**Dialog:** deleted. «افزودن محصول» pushes `/products/add` directly, `kind` starts `'physical'`,
and step ۱ is the only place it is ever chosen. The `?kind=` query param went with it — nothing
produced one any more, so reading it was dead code.

**Steps ۶ and ۷:** while the card is unlocked (no live axis) it now reads AND writes
`variants[0]` — the row that IS the product — instead of only the seed. `baseStock`/`basePrice`/
`baseCompare`/`baseInfinite` are still written alongside, because the implicit row carries no
option values and so never matches `donorOf`: the seeds are what the rows generated by the FIRST
axis inherit. Locked (real variations exist), the card is display-only over the seeds, as before.

**Unlimited:** a new `baseInfinite` form field plus a labelled switch on the quantity card,
matching the discount switch on the price card. It maps to `trackInventory: false` through the
existing `variants[].infinite` → payload path — no backend change. Turning it on clears the count
(a leftover would be sent as `initialStock` and rewrite the ledger of an untracked variant), the
same rule `VariantLeafRow` already followed.

`useVariantSync` seeds `infinite` onto **every** generated row, not just the first, because ∞ is a
tracking MODE rather than a quantity — the rule its own donor branch already applied.

### Why the discount switch lost its `useState`/`useEffect`

`BasePriceSection` kept `onSale` in local state with an effect re-syncing it from `baseCompare`,
plus a `lastLocal` ref so clearing the field mid-edit did not flip the switch off under the
cursor. Now that the card is bound to the row, the row's stored `hasDiscount` flag — which exists
for exactly this reason — answers the question directly, so all three were removed.
